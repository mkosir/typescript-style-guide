## About Guide

### What

Since "consistency is the key", TypeScript Style Guide strives to enforce the majority of rules using automated tools such as ESLint, TypeScript, Prettier, etc.
However, certain design and architectural decisions must still be followed, as described in the conventions below.

### Why

- As project grow in size and complexity, maintaining code quality and ensuring consistent practices become increasingly challenging.
- Defining and following a standard approach to writing TypeScript applications leads to a consistent codebase and faster development cycles.
- No need to discuss code styles during code reviews.
- Saves team time and energy.

### Disclaimer

Like any code style guide, this one is opinionated, setting conventions (sometimes arbitrary) to govern our code.

You don't have to follow every convention exactly as written. Decide what works best for your product and team to maintain consistency in your codebase.

### Requirements

This Style Guide requires:

- [TypeScript 5](https://github.com/microsoft/TypeScript) or later
- [typescript-eslint v8](https://github.com/typescript-eslint/typescript-eslint) with [`strict-type-checked`](https://typescript-eslint.io/linting/configs/#strict-type-checked) configuration enabled.

The Style Guide assumes but is not limited to using:

- [React](https://github.com/facebook/react) for frontend conventions
- [Playwright](https://playwright.dev/) and [Vitest](https://vitest.dev/) for testing conventions

## Agent Skill

The [Agent Skill](https://github.com/mkosir/typescript-style-guide/tree/main/skills/typescript-style-guide) complements TypeScript, linters, and formatters. Those tools enforce automatable rules. The skill helps coding agents apply, review, and explain conventions that depend on context and judgment.

It provides a shared reference while loading only the guide sections relevant to the task, not the entire guide. This keeps unrelated guidance out of the coding agent's context while supporting consistent decisions across a codebase.

## TLDR

- **Embrace const assertions** for type safety and immutability. [&#11107;](#const-assertion)
- Strive for **data immutability** using types like `Readonly` and `ReadonlyArray`. [&#11107;](#data-immutability)
- Make the **majority of object properties required** (use optional properties sparingly). [&#11107;](#required--optional-object-properties)
- **Embrace discriminated unions**. [&#11107;](#discriminated-union)
- **Avoid type assertions** in favor of proper type definitions. [&#11107;](#type--non-nullability-assertions)
- Strive for functions to be **pure**, **stateless**, and have **single responsibility**. [&#11107;](#functions)
- Maintain **consistent and readable naming conventions** throughout the codebase. [&#11107;](#naming-conventions)
- Use **named exports**. [&#11107;](#named-export)
- **Organize code by feature** and collocate related code as close as possible. [&#11107;](#code-collocation)
